# alt self-hosted server

The server contains the native/Git data plane and the complete workbench. It uses a dedicated PostgreSQL 18 database and a local POSIX byte volume. No Cloud account is required. This distribution is an internal candidate until its acceptance record is complete; it does not replace the older `deploy/` installation.

## Build an offline bundle

Use Docker Engine with Buildx and Compose, Python 3.11 or newer, and an Internet connection for the build. Docker's classic image store and its containerd image store both work. Build from an explicit source checkout. On a shared runner, follow its build-lock policy; the image compiles Rust and must not overlap a performance measurement.

```sh
python3 scripts/package-server.py --architecture amd64 --output /tmp/alt-server-amd64
python3 scripts/package-server.py --architecture arm64 --output /tmp/alt-server-arm64
```

Each invocation builds one architecture from the same sources, checks that the inputs did not change, and exports the app, PostgreSQL and HTTPS edge in `images.tar`. `dependencies.json` fixes upstream versions and multi-platform manifest digests. The bundle records the source digest, origin image handles, portable OCI configuration digests, architecture and file hashes. On import, the installer verifies the exact serialized image configuration and ordered layer identities, then pins the corresponding immutable local Docker handles. This supports both classic and containerd image stores, whose displayed image IDs differ for the same content. Cross-built images explicitly record that native execution has not yet been checked; this must be covered by target-host acceptance.

The Dockerfile builds the Rust binary and workbench from this checkout, including the licensed, versioned shared UI archive. It never clones a moving branch or fetches a private package. The runtime includes matching PostgreSQL clients and age 1.3.2 for encrypted backups. Building requires network access; loading and operating the completed bundle do not.

Transfer the complete bundle and its independently obtained `bundle.json` SHA-256 to the installation host. Verify that checksum before trusting the included program. Its file hashes detect damage but do not establish publisher identity on their own.

## Prepare and initialize

Linux amd64 and arm64 Docker hosts are supported. Supply a certificate and private key for the public HTTPS origin; a private CA works offline if clients trust it. The default bind address is localhost. Use `--bind 0.0.0.0` only when this edge should accept remote connections. The origin's port is the published host port, default 443.

```sh
python3 /path/to/bundle/manage.py load --bundle /path/to/bundle
python3 /path/to/bundle/manage.py prepare \
  --bundle /path/to/bundle --directory /srv/alt --project alt-local \
  --origin https://alt.example.org \
  --certificate /secure/fullchain.pem --private-key /secure/key.pem \
  --bind 0.0.0.0
python3 /path/to/bundle/manage.py initialize --directory /srv/alt
```

When another reverse proxy on the same host owns the public port, add `--https-port 8443` (any free local port): the edge then listens on that port of the bind address, and the front proxy forwards the public origin to it. Load the bundle into the destination Docker engine before preparation. Both commands verify the loaded content; preparation refuses missing or mismatched images and records the verified local handles in `bundle-identity.json`. The destination must not exist. Preparation generates a unique installation/workspace identity, a receipt key, database password, short-lived operator credential and initial browser password. It prints paths, never their contents. The application and edge run with the preparing user's nonzero UID/GID; root preparation uses 9000:9000 unless explicitly overridden. Keep the installation directory private.

Initialization explicitly creates the database schema, claims the first local administrator and enables the configured browser origin. Sign in as `owner` using the password in `/srv/alt/operator/initial-password`. The operator token expires after one hour. These bootstrap files are mounted only into explicit operator jobs, not the running application. Password changes and administrator recovery use the same server operator; see [server operator guide](../crates/alt-server/README.md).

Initialization does not silently resume, migrate or replace an existing instance. If a step fails, retain its output and inspect the original database/configuration. Restarting is not permission to initialize again. The explicit `alt-server initialize --resume`, password recovery and token recovery operations are available for reconciliation; the wrapper does not guess which partial action completed.

The application counts sign-in attempts, requests under way and request bodies by the address they come from. It reads that address from `X-Forwarded-For` only where the connection comes from a proxy named in `http.trusted_proxies` of its configuration, and then takes the last address in the header that is not such a proxy. The prepared configuration names the packaged edge (`127.0.0.1`, `::1`: the edge shares the network namespace of the application) and the gateway of the network of the edge, which is the address a proxy on this host reaches the edge from.

Whether another proxy stands in front of the edge is one line of `.env`, `ALT_FRONT_PROXY`:

- Empty, which is what `prepare` writes: the edge is what callers connect to. It takes a caller for whoever connects and passes on nothing a caller says of its own address. Use this with `--bind 0.0.0.0`.
- The gateway of the edge network (`ALT_GATEWAY` in `.env`, `172.30.91.1` unless `prepare` was given `--subnet`), which is what `prepare --front-proxy` writes: a reverse proxy on this host forwards the public origin to the edge, and the edge passes on what that proxy says of the address of a caller. Use this with the default bind address and `--https-port`. Without it every caller behind that proxy is counted as the one address the proxy connects from: all of them then share the sign-in attempts and the 32 requests one address may have under way.

Do not name the gateway where the edge port is reachable by anyone but that proxy: whoever connects through the gateway is then believed. The front proxy has to set `X-Forwarded-For` itself and not pass on what it was sent; Caddy does so unless it is told to trust its callers. After changing the line, run `docker compose up -d --wait`.

The network of the edge has a fixed subnet, `172.30.91.0/24` unless `prepare` was given another with `--subnet`; a second installation on one host needs its own. An instance prepared by an earlier version has neither the subnet nor an entry for its proxies: see the upgrade steps below, where `migrate` writes the entry. An instance with no proxy named counts every caller as the edge and says so in its log, as a `background.failed` event of the task `configuration`, each time it starts.

`http.body_timeout_ms` changed its meaning with this version. It was the time a whole request body had to arrive in; a push that took longer was refused however steadily it came. It is now the time a body has to move in: in every such window at least 1024 bytes a second have to arrive on average, a body that does is received however long it takes, and one that stalls is given up within two windows. `http.connection_timeout_ms` likewise no longer ends a connection on which a request or response body is moving; it counts from the last piece of a body. A configuration prepared by an earlier version has `"body_timeout_ms": 60000`: it keeps working, and now means that a stalled upload is given up after one to two minutes; new configurations use 30000. No worker is held while a body arrives, and the bodies one address and the whole instance may have under way are bounded by `http.receiving_each` and `http.receiving_megabytes`, so slow uploads take none of the capacity other requests run on. A response is held to the same pace while its reader takes it, with the time the application waits for the reader counted in such windows; a reader that takes nothing is let go of within two of them, where earlier it kept its connection until `http.connection_timeout_ms` had passed.

One address has a part of the connections in use at once and no more: `http.connections_each`, a quarter of `http.connections` where the key is absent, counted for each address the edge names, so a client that has that many requests under way is answered `429` with `Retry-After` for the next until one ends. Earlier versions had no such limit. A clone, a fetch or a push of Git has one request under way at a time: with the example configuration 32 of them from one address go on at once. Raise the key where many people or build jobs share one address, behind a network translation for instance.

The packs of pushes are verified within one amount of memory, `http.indexing_megabytes` (4096 where the key is absent, as in every configuration prepared before this version; see the server operator guide for what a pack takes of it). Earlier versions bounded what one pack inflated to but not what the packs verified at once held in memory. A push that finds the memory taken by other pushes now waits for it, for half of `http.work_timeout_ms` at the longest, and is then told to push again.

While it serves, the application writes what it holds for a time (request bodies being received, responses to fetches being sent, the bases of deltas of a pack being verified) under `data/temporary`, on the disk of the data, in a directory that is its own (mode 0700) and that it empties when it starts. Earlier versions wrote these to `/tmp`, which this package mounts as memory of the container: a push of a few gigabytes then counted against `ALT_MEMORY`. `/tmp` is still what the operator commands (`backup`, `restore`) write to, and `ALT_TEMP_BYTES` its size. On the data disk the request bodies that are received or wait for a worker take up to `http.receiving_megabytes` (four of the largest request where the key is absent, 16 GiB with the limits of the example) and each worker has one more, the files of bases of all pushes together up to `http.indexing_megabytes`, and each response to a fetch that is being sent what it holds.

Memory. The application container is limited to `ALT_MEMORY`, 2g unless set. What the server takes at the most with a configuration prepared by this package: 1376 MiB for the packs of pushes being verified (`http.indexing_megabytes`, which `prepare` now writes into the configuration at the least the limits allow), 128 MiB for the two passwords that are checked at once, and what its eight workers hold of the requests they answer, of which each reads a body of at most 8 MiB and writes a page of at most 8 MiB. The last amount has no single number in the code and was not measured; the first two are bounds the server keeps. With `http.indexing_megabytes` at 1376 a pack takes 268 bytes of that for each of its entries, so a push of more than about three million objects in one pack is refused (`server limit exceeded: index memory`) until the key and `ALT_MEMORY` are raised together: keep `ALT_MEMORY` at least 1 GiB above `http.indexing_megabytes`. A configuration prepared by an earlier version has no such key and the server then takes up to 4096 MiB for packs, more than the 2g of the container: add the key, or set `ALT_MEMORY` to 6g or more, before upgrading.

The application root filesystem is read-only, capabilities are dropped, and data/temp mounts are separate. PostgreSQL has no TCP listener or published port. Its local socket requires SCRAM authentication. The application only listens on loopback in the edge's network namespace; only the HTTPS edge port is published. The packaged services never need the host Docker socket.

## Daily operation

Use the prepared directory's Compose file and environment for start/stop/status. Avoid `down --volumes`: it deletes the PostgreSQL volume. Byte files and the private receipt key alone are not a complete instance.

```sh
cd /srv/alt
docker compose up -d --wait
docker compose ps
python3 /path/to/bundle/manage.py operator --directory /srv/alt -- status
python3 /path/to/bundle/manage.py operator --directory /srv/alt -- audit --limit 50
```

`/livez` only reports that the HTTP process responds. `/healthz` opens the persisted instance and checks its current schema/identity. Neither is a backup drill or a full scan of object bytes. Instance administrators see read-only counters, old recovery gaps, the last recorded restoration and paginated operation history in Settings. Ordinary members cannot access this information. Stored byte counts include each repository's stored blobs; they are not a host-disk-usage measurement.

Create repositories, grants and policy with the server's operator commands. For example, `operator ... -- repository-create example --quota-bytes 1073741824` creates a repository; the administrator still needs explicit repository grants to read or publish. Native endpoints and `/git/<repository>` share the same publication authority.

The application removes nothing from the content store by itself. Content that no publication retains any more (uploads that were abandoned or expired, what a refused request brought, the content-store copies an upgrade released) and the segments it leaves empty stay on the data volume until `collect` is run for the repository: `operator ... -- collect example --limit 1000` removes up to that many unretained contents and reports the count as `removed`. Run it for every repository on a schedule, and again while it reports as many as its limit. Requests, sessions and credentials that are over, and pack segments that a merge replaced, are removed by the application.

After the bootstrap token expires, generate a new private token and use `recover-local-token owner` with a reason and an expiry no more than one hour ahead. This requires physical access to the instance configuration/key/database, revokes old authority, and is audited. Do not extend an old token by changing its file.

## Backup, upgrade and restoration

Keep an age identity outside the server. The public recipient may be used on the server. An operator can explicitly mount a private output directory with `--mount /external/backup:/backup` and invoke `backup --recipient age1... --output /backup/new-run`. Give that directory to the configured application UID. Budget enough temporary space for the SQL dump and, during verification/restoration, the decrypted package; the default temp mount is 4 GiB. Larger instances need an explicitly sized private temp volume.

Backups encrypt SQL, object bytes, configuration and the receipt private key. A signed manifest contains visible repository IDs, refs and sizes, so the output directory is still private. `backup.started` and `backup.created` entries share an operation ID with the manifest. A missing completion record or `backup.unconfirmed` requires checking the original output package; it does not prove rollback. Historical schema backups have no database audit table and rely on their signed completion marker.

Copy the completed package off the server, verify all entries with `backup-verify`, and restore it to a separate empty database and absent data/key paths. A verified package is not a completed restore drill. `restore` requires explicit source fencing, raises runtime/repository generations, revokes credentials/sessions, preserves historical receipts, and leaves old unfinished requests with unknown results. It refuses an existing destination instead of overwriting it. Interrupted restoration reports an unknown stage and cannot be made safe by simply starting the service.

Upgrade only after a verified external backup, in this order. (1) Stop the application (`docker compose stop app`) and back up with the version that is installed, whose commands read the configuration as it is: add no key of the new version to it. (2) Load the new bundle (`manage.py load`), put its `compose.yaml` and `Caddyfile` in the place of those of the installation directory, and set `ALT_IMAGE`, `ALT_DATABASE_IMAGE` and `ALT_EDGE_IMAGE` in `.env` to what `load` printed; where a proxy on this host stands in front of the edge, add `ALT_FRONT_PROXY=172.30.91.1` to `.env`. A `Caddyfile` changed by hand is replaced by this: the packaged one takes the front proxy from `.env`, and needs no change for it. Where `172.30.91.0/24` is taken on the host, also set `ALT_SUBNET` and `ALT_GATEWAY` in `.env` to a free private network and its first address, and use that gateway for `ALT_FRONT_PROXY`. (3) Run `migrate` with the new version, writing the new configuration to a directory mounted for it (`operator --mount /srv/alt-next:/next -- migrate --from-schema N --output-config /next/config.json`). It writes `http.trusted_proxies` (the edge and the gateway) and `http.indexing_megabytes` where the old configuration had none. (4) Make any other change to the configuration it wrote, put that in the place of `config/config.json`, check `health`, and start everything with the `manage.py` of the new bundle: `python3 /path/to/new-bundle/manage.py start --directory /srv/alt`. It makes the edge anew on the network with the fixed subnet, and the application with it. Plain `docker compose up -d --wait` is not enough here: Compose keeps a network an older Compose made, which carries no digest of its configuration, on the subnet Docker chose for it, and says nothing; the edge then sees the proxy on the host from another gateway, and every caller is one address. `start` takes such a network down first (`docker compose down`, the volumes kept) and fails where the network is still not the one written in `.env`.

The same in the words of the server operator: stop application writes, load the new exact image, and use its explicit `migrate --from-schema N --output-config /path/to/new-config.json` on the same dedicated storage. Review the produced config and health result, then switch the mounted config and application image. This release upgrades from schema 18, 19, 20, 21 and 22 (`--from-schema 18` to `--from-schema 22`, the schema the instance is at), and backs up and restores schema 18 to 23. An instance at schema 17 or older is first upgraded to schema 18 with the last release that carries those migrations and backed up again there; the current operator refuses it, and a backup taken at schema 17 or older, with a message that names this step, and changes nothing. A new instance is created directly at the current schema. An older binary must reject the new schema. There is no automatic downgrade after new writes. Retain source data and separately plan any return path. `migrate` is for an instance of this package and refuses the configuration of a Cloud instance, whose schema moves with its platform generation. Keep a copy of the old configuration file, and keep the file itself as it is until the new one is in use: `migrate` reads it and writes the new one beside it, and a `migrate` that is run again after a failure has to find the old file unchanged and refuses an output file that differs from what it would write.

Upgrading from schema 18 also changes where published Git objects are kept. That version stored each natively published object twice: in a pack segment and in the content store. The upgrade moves the objects that are only in the content store into pack segments, removes the content-store copies of all of them, and recounts each repository's stored bytes as its pack segments plus the task content it retains; the count is usually lower afterwards. This runs inside the same `migrate` transaction. Stop the application first, as for every upgrade. Nothing changes unless the whole upgrade commits, so a failed or interrupted run is repeated with the same arguments; if a repository's objects cannot be moved the command fails and the database stays as it was. Allow time in proportion to the objects being moved, and free space on the data volume for one more copy of them: the released copies are removed by the next garbage collection, not by the upgrade. Backups taken at schema 18 restore under the new version, which converts them the same way.

Upgrading from schema 19 changes how a committed publication is stored. That version kept the whole publication, with every ref update of the push, four times; now the request holds it once and the audit record stays whole, while the stored result of the request and the outbox event keep the receipt without it and reads put it back. Receipts, signatures and responses do not change. The steps are the same as for every upgrade: stop the application, run `migrate --from-schema 19 --output-config ...`, review the health result, switch the config. The rewrite runs inside the `migrate` transaction and checks every row it changes; if one would not read back as before, the command fails and the database stays as it was. Allow time in proportion to the number of committed requests. Backups taken at schema 19 restore under the new version, which converts them the same way.

From schema 20 the publication documents are compressed with lz4, which the PostgreSQL server must be built with. The bundled PostgreSQL image is. An instance that uses another PostgreSQL server needs one built with `--with-lz4`, as the official images and distribution packages are; `initialize`, `migrate`, `health` and the application refuse a server without it and say so. Values stored before the upgrade keep their previous compression and stay readable.

Upgrading from schema 20 removes the foreign key from a ref to its repository, which the database checked once for every ref a push created. No row changes, and the step takes no time in proportion to the data. Backups taken at schema 20 restore under the new version, which applies the same step.

Upgrading from schema 21 records when each request ended and when each credential was revoked, because the server now removes what has been over for long enough: a finished request after 30 days, sessions and device credentials 30 days after they ended, and a credential 90 days after it ended. The steps are the same as for every upgrade: stop the application, run `migrate --from-schema 21 --output-config ...`, review the health result, switch the config. The command adds the columns and three indexes and writes the revoked credentials; it does not write the requests. Building the indexes reads every request once: about three seconds for a million requests, and the table keeps its size. The running server then gives the finished requests their moment as it goes, 20,000 every half minute, and vacuums the table after each round, so a million requests take about 26 minutes and the table grows by a few percent (about 4% in that measurement) instead of doubling; no extra disk has to be set aside. `alt-server health` shows how many are still waiting as `requests_awaiting_settled_at`, which reaches 0 and stays there. A committed request is given the moment in its receipt; a rejected or expired one the moment the server comes to it, and a revoked credential the moment of the upgrade. Until a request has its moment it is not removed, so nothing that ended before the upgrade is removed sooner than 30 days after it (credentials: 90). The server answers the same before and after this is done; only the removal waits for it. One behavior changes for clients: a request ID that was committed more than 30 days ago is no longer answered with the old receipt and counts as a new request. Requests that published task records, and the audit records, are kept for good. The full table is under "Retention" in the server operator guide. Backups taken at schema 21 restore under the new version, which applies the same step.

After an upgrade from a version that served Git pushes before this one, read the stored objects once: `python3 /path/to/bundle/manage.py operator --directory /srv/alt -- scrub`. It reads every object of every repository's pack segments the way a fetch does and holds each against its id; `"unread_objects": 0` means all of them are read. Earlier versions accepted a pack that carries one object in several entries, one of them at the end of a very long delta chain, and wrote an index for it that sends reads of some objects past what is read (`segment corrupt: delta chain`). Git itself writes no such pack; one made on purpose could be pushed. `scrub --mend` replaces each such segment by the same pack with its index made anew, and reads it again; a segment whose pack no longer verifies is left as it is and named with `kept_because`, and is restored from a backup. The command may run while the application serves. A segment that was replaced leaves the disk like one a merge retired.

The full command arguments, trust-key handling, generation selection and failure recovery rules are in the included [server operator guide](../crates/alt-server/README.md). Disaster recovery packages contain secrets and preserve installation identity; they are not the portable cross-mode migration format. The same guide covers `alt portable` exports, explicit identity mapping, empty-target import and source cutover. Fresh configurations enable bounded portable transfer; existing configurations require an explicit operator opt-in.
