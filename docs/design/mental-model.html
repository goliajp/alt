§ 0 ─ framing

"满足各种爱好" 与 "限死" 是假二选一。

通用工具都走第三条路 · strong invariants + weak style

你纠结的二选一(对齐 git 的爱好 vs 限死)是平行视角的对立。 所有"通行 + 大家都舒服"的产品都不是其中之一——它们都精挑出 一组真不能妥协的事强制锁住,其他完全放开。

git 自己的问题恰恰是 invariants 太薄——只锁 hash chain、content addressable、DAG,所有"协作形态"全让用户拼。所以才有 GitHub Flow / TBD / git-flow / stacked diffs 几大流派打架,AI 在中间漂移。

alt 的灵魂位置:
底层强 invariants(签名、op log、portable patch、workspace、git 兼容、immutable history)
中间 flow 是可换 preset
顶层 surface 按"用户当下的需求维度"暴露概念,不按用户类型分

这样既不像 git 那样让用户自己拼到漂移,也不像我 v1 提的 task model 把所有人锁死——alt 像 Postgres 一样硬 invariants、像 ESLint 一样可换 preset、像 vim 一样可适配多种风格。

另外两条架构原则同样不可妥协: alt ⊇ git 三轴(format-native § 6 · visibility 场景 84 · structured commit msg 场景 85 — alt 仓比 git mirror 多三层信息) + LLM 隔离(场景 86 · core 0 LLM · 增强 well-defined · invariant 7 候选)。

这 ⊇ 关系的真正动机(§ 13): alt 替 git 兜住 AI 时代所有的脏乱差 · 给 git 出口永远 polished。 AI agent 在 alt 里狂奔(N 次试错 / 反复 undo / 探索性 commit / 内部 prompt 痕迹 / 真实 secrets / .env / API keys) · git mirror 上依然是干净的 conventional commit + 0 secret 泄露。 alt 在 local 还主动接管 OS keychain + 各种工具链访问(npm / aws / gh / docker / ssh / LLM api keys ...) · 不回避密钥这件事,正面把它做好。git 历史可读性跟 AI 产出力本质冲突,alt 是编辑学缓冲 — 这是它跟 git 共存而非替代的根本理由。

alt 的两个正交维度 · 最高抽象

alt 完全面向交付。交付的对象可能是别人(协作者 / GitHub / 客户 / 社区)· 也可能是自己(里程碑标记 / 阶段成果 / 复盘)— 哪怕交付给自己,也是一次交付。

但每一次交付前必有工作室。工作室里脏乱差是常态:真凭据 / .env / 反复试错 / 失败 task / 半成型讨论 / agent fix.suggest 痕迹 / 用过即丢的 prompt。 alt 替你把工作室装得下,只在交付边界做编辑学(§ 13)。 这跟 git 共存而非替代的根本理由 —— git 不允许工作室存在(它假设你已经"准备好交付"才 commit)· alt 反过来:工作室一等公民,交付是其上的视图。

§ 1 ─ invariants

底层 6 件事 — 永远成立。

alt 的灵魂在这里 · 切 preset 不动它们

下面 6 条是 alt 比 git 多锁的东西。git 只锁 3 件(hash chain、content addressable、DAG),alt 再加 6 件——这 9 件加起来,是无论用户走哪 种 preset 都不会塌方的底。

这 6 件每一件都是设计 bet,但每一件都有 prior art 撑腰——不是 凭空发明,而是把别的 VCS 验证过的好做法都强制成默认。

i.

Signed Op

每一次状态变更都签名归属。AI / human / fork 都是 first-class actor,签名身份强制 attach。

why"谁做了这个改动" 永远可问。AI-coding 时代追责必须可信。

ii.

Op Log

append-only 的操作历史,不只是 undo 工具——是 navigation primitive。可以"回到 3 小时前的状态"。

priorjujutsu 的 op log。alt 把它做成一等公民 UX,不藏在专家层。

iii.

Portable Patch

任何 change 都能序列化成内容寻址、签名的便携 patch。pull / send / sneakernet 都是同一格式。

priorgit format-patch + Pijul patch theory。alt 让它成 protocol-level 一等公民。

iv.

Workspace

每个 actor 一个隔离沙盒,并发安全。多个 workspace 可在飞, 互不踩。

priorPlastic SCM + git worktree + jj working copy。alt M5 已落地。

v.

Git Compat · L1 语义保真

L1 语义保真(VISION § 3 推论 + § 8.1 拍板): 所有 commit / tree / blob / tag 的 git hash 不变 · refs / HEAD / 用户 config 还原 · export 的 alt → git 在 git 视角下语义等价。 L2 物理形态不追求:packfile 布局 / ref 物理后端(reftable/files)/ loose↔packed 等是 git 内部自由度,export 写 files 后端并归一化即可。

whyalt 的 north star。 L1 是结构性保证(canonical 字节保证 hash 计算可重现),不靠测试;corpus_roundtrip 自动化封缄。 没这个 alt 就是另一个孤立 VCS,不能跟 GitHub / IDE 共生。

vi.

Immutable History

commit 一旦写下不可消失。amend / rebase 创建新 commit,旧 的留在 op log 里可追溯。

why跟 git 一致。 AI 操作不允许"消失",任何动作都可审计。

§ 2 ─ preset

中层 flow preset — 像 ESLint 的 config。

user 选口味 · 底层 invariants 不变

preset 不是 "mode",不是把 alt 配成另一个工具。它是装在 invariants 之上的一组 validator + lifecycle 命令,告诉 alt: "我用 GitHub Flow / TBD / AVH 的规矩工作,请按这些规矩 lint 我"。

preset 之间切换不影响 commit 历史、不影响签名、不影响 op log——只 影响:用什么命令、什么时候报警、reviewer 怎么派、release 怎么 cut。

第一批 ship 4 个 + 1 个 custom slot。后续 preset 是社区可扩展点, 类似 ESLint 的 shareable config。

§ 3 ─ protocol

不管哪个 preset, change 都走同一条 protocol。

produce · sign · review · land

review / land / patch 是 protocol-level,不是 workflow-level。任何 change 不管在哪个 preset 下,都按 produce → sign → review → land 四步流转。preset 提供的只是 transport(怎么传、怎么呈现、 怎么 gate)。

这是 alt 在底层 invariants 之上加的一层"协议骨架":AI 不需要 理解每个 preset 的 quirk,只需要按 protocol 行事——底层 protocol 不变,上层 preset 把它投影成 PR / Gerrit Change / stack push / mailing-list patch / AVH feature-finish 等不同 transport。

这一层是真创新。把"如何把一个 change 送到 main" 抽象成单一 protocol,跨 preset 复用,是其他 VCS 都没做的。

图 3 · 协议层

无论 preset 是 PR / stack / AVH finish / mailing-list,所有 change 都走 produce → sign → review → land 同一 protocol。preset 只是 transport 的差异。

§ 4 ─ dimensions

4 个需求维度,不是 4 类用户。

D1 写代码 · D2 管 change · D3 协作 · D4 治理

修正 v2 的早期错误:不能假设"单人 = 简单 surface、团队 = 复杂 surface"。一个 AI agent 单干很可能比 10 人团队更复杂——它要 review 自己历史、undo 错误、跨多 change 并行、解 op log。actor 数 量不等于心智复杂度。

正确的轴是 当下的工作类型:你在写代码?管理一个 change 的生命周期?跟别人协作?治理 / 审计? 不同维度暴露不同概念。同一个 user(包括 AI、包括单人、包括团队) 会在同一天里跨好几个维度。

4 个维度按"心智负担递增"叠加,但顺序不绑死用户类型:

D1 · 写代码——commit / branch / remote。 git 用户已熟。任何人起步。
D2 · 管 change——change(atomic 单位) / op log / undo。jj 风格的精细化。
D3 · 协作——preset / workspace / review。 选口味 + 多 actor 同 repo。
D4 · 治理——policy / codeowners / audit。 合规、capability 强制。

每个 D 是同一个 user 按需触达,不是不同 user 看到不同 menu。AI agent 一上来就可能跨 D1+D2+D3——这是常态,不是异常。

关键区别 "概念暴露"是按需驱动的,不是 alt 强制递进。用户做什么触达 哪个 D:
  • "我刚刚 commit 错了" → 触达 D2 的 undo 和 op log
  • "我要跟 alice 一起做这个" → 触达 D3 的 workspace 和 review
  • "这次改动碰了敏感路径" → 触达 D4 的 codeowners
不是 alt 隐藏命令,是 user 在不碰到那个场景时不需要那个概念。

step 3 · git 出口 · author 聚合(§ 13 编辑学职责 #4)

alt 静默做了 · 推 git 时 author 自动聚合
  • alt 仓内 commit author 是 claude-a@local / cursor-b@local / ci-bot@local 等 ai-agent / bot · git mirror 看不到这些非人类 identity
  • 聚合规则:ai-agent / bot 的 commit · git author = controlling human(work@company.com)· git committer 可选保留 alt agent id 作为审计痕迹(可关)
  • 多个 ai-agent commit 被 squash 进 1 个 git commit 时 · co-authored-by 全部列上(可选)
  • alt op log 保留真实 identity 链(谁起 task · 谁实际跑 commit · 谁批 finish)· git 仓只展示对外责任人
  • 对外 git 仓的 "Verified" 签名落到 controlling human 的 GPG / SSH key · agent 不签 git 对外 commit
为什么这么设计 · 三条原则共同推出

这一聚合规则不是 ad-hoc: (1) § 13 编辑学职责 — 对外 git 仓不暴露 AI 内部协作细节; (2) invariant 1 signed op — 对外签名必须有可问责人类站后面,agent 不能独立签; (3) invariant 7 LLM 隔离 — agent 的所有动作必须挂 controlling human · 这就是这个挂载的对外兑现。 三条原则共同推出:agent 自由产出 · controlling human 承担对外责任。

§ 6 ─ format-native

每种格式自己的 history / diff / edit。

owner 战略重点 · alt 跟 git 最大差异 · git 历史包袱补不了

每个格式场景看 4 件事: 1. 这格式 today git 怎么糟 · 2. alt 该怎么做(目标体验) · 3. alt 今天哪个 prism / 命令 ship · 4. 缺哪些。

§ 9 ─ Web UI

secrets · 权限 · alt 仓的安全语义

owner 的核心 framing — 不用考虑那么多 · 尽情维护真实开发状态 · 我们只在交付层上做好。

意思是: alt 仓 = 真实开发环境(secrets / .env / API keys / 内部讨论 / 权限矩阵 / 全部该进就进)· git mirror = 公开交付(只见 polished 标准 git 仓)。 agent 在 alt 里直接看到真实凭据 / 真实权限,debug / 跑起来不打折; git 那一侧 0 泄露,公开仓库 scanner 跑不出任何 token。

具体怎么实现"alt 仓装得下而且安全" — 四层防御:

  1. 第 1 层 · alt-only path 分类 — 跟 .claude/ 同机制 · 把 secret 类 path(.env* / secrets/ / *.pem / 任何带 password/token/key 关键字的文件)默认标 visibility=alt-only-secret。push --to git 时 path filter 切掉。
  2. 第 2 层 · 仓内加密存储 — secret 类 atom 在 alt 仓本地也是加密(age / sops 兼容的内置后端),只有 owner 当前 identity 解锁。AI agent 跑 task 时 alt 临时 unlock 注入 env · 流程结束自动 lock 回去 · agent 看不到密钥实体。
  3. 第 3 层 · server-side ACL — .altserver 远端仓本身按 identity 受 ACL(成员名单是 alt-only kind atom)· github 仓全开但 alt 仓限内部。一份 source · 两套可见性。
  4. 第 4 层 · push hard gate — push --to git 必跑 secret scan(基于内置规则 + alt-only-secret 分类)。检出任何 secret material 在 commit / message / branch name 中 → push 直接 reject + 详细报错 + 提示哪条转 alt-only。CI 同步跑 mirror 端 scan 兜底。

关键:secret 是 alt 仓里的一等 atom(alt://kind/secret)· 有自己的 lifecycle(rotate / expire / revoke)· 进 op log · 可 undo · 可审计谁什么时候用过哪个 key。 git 那一侧永远不会看到 secret 任何残影 — 即使 alt 内部加密被破 · git mirror 上根本不存在 secret commit,attacker 没有 surface。

跟 vault / secrets-manager 的区别

vault / 1password / AWS Secrets Manager 是独立服务 · 跟代码仓分离 · agent 要专门去拉 · 每个环境 (dev/staging/prod) 单独配置。alt 把 secret 当成仓的一部分 · 跟代码同 ref / 同 commit / 同 history · agent alt checkout 一份就齐全。

跟 git-crypt / git-secret 的区别

git-crypt / git-secret 在 git 仓里存加密 blob · 一旦 push 到 github · attacker 拿到密文可以离线 brute · 一次密钥泄露全历史可解。 alt 走不同路:secret 永远不进 git mirror · attacker 在 github 上根本看不到加密 blob 存在 · 0 surface。

关键论点 · agent 视角

AI agent 不需要"写得节制"才能产出干净的 git 历史。agent 在 alt 里完全自由地反复迭代, finish 时 alt 替它做编辑学:squash · 重写 message · 抹 AI 元数据 · 聚合 author。

git 那一侧拿到的永远是人类提交的干净 conventional commit。 协作者 / open source 社区看不到 agent 怎么"挣扎着写出来"的过程。

关键论点 · 人类协作者视角

owner 内部用 alt 时享有所有 AI 时代的便利(workspace 隔离 / op log 回溯 / 结构化 commit msg / format-native diff)· 但交付给 git 协作者的永远是一份标准 git 仓。

github 社区贡献者 / 不用 alt 的同事打开 git 仓看到的就是标准 conventional 提交, 感觉不出来 alt 在背后兜了多少脏。

命令 用途 编辑学职责 7 件
alt export <dir> 单次快照导出 — 把当前 alt 仓状态写成一个新的 git 仓目录。一次性、本地、无 remote。 3·path filter / 4·author 聚合 / 5·branch filter / 7·secret hard gate 全部应用。1·squash / 2·message 降级 应用(可配)。6·LFS conversion 应用(若启用 LFS profile)。

关键判断:7 件编辑学职责不在 commit 时发生 · 也不在alt 仓内部 sync 时发生 · 只在 push/export 出口边界发生。alt 仓内日常用所有职责都不动 — agent 自由产出 · owner 自由 commit · multi-identity 自由切换 · secret 自由 inject — 所有这些"脏乱差"留在 alt 仓内部完整 · 只在跨出口时统一过滤。 这是 alt 跟 git 共存而非替代的关键架构选择(§ 0 framing + § 13 motivation 的兑现位置)。

alt 的编辑学职责(curation responsibility) 在 alt push <remote> / alt export <dir> 这两个出口命令中集中行使,具体做这 7 件事:

  • 1 · squash 策略 — feature 分支按 owner 配置的策略(per-task / per-day / per-author)squash 成 N 个 git commit,N 通常 ≤ 3。原始微 commit 链保留在 alt op log。
  • 2 · message 降级 — 结构化 commit msg schema 抽出 title / body / closes 三段,降级成纯文本 conventional 格式。AI 元数据 / fix.suggest / token cost 全部丢弃(只留 alt 内部)。
  • 3 · path filter — visibility=alt-only 的文件/目录(.claude/ 等)在 git mirror tree 里直接不存在。同一 commit 在 alt 和 git 两侧 oid 不同(superset-oid ↔ subset-oid 映射,axis 2)。
  • 4 · author 聚合 — alt 里 author 可能是 claude-agent-001 / cursor-agent-002 · git author 统一聚合成人类 owner(committer 可选保留 alt agent id 作为审计痕迹)。
  • 5 · branch filter — alt 的 wip/* / tmp/* / abandoned task 分支不推 git。git 只看到 main / develop / release/* / hotfix/* + 已 finish 的 feature。
  • 6 · LFS conversion — alt 的 CDC chunk store 实体不推 git · 转成 LFS pointer · 大文件实际数据走 alt 服务器或独立 LFS server。
  • 7 · secret hard gate — 跟 path filter 不同 · 这是reject 不是filter。push --to git 强制跑 secret scan(alt://kind/secret 分类 + 内置 entropy 规则)· 检出任何 secret material 在 commit / message / branch name 中 → push 直接拒绝。CI 同步跑 mirror 端 scan 兜底。这是唯一会让 push 失败的编辑学职责。

alt 不只是存 secret · 主动接管 keychain + 工具链访问

alt 在 local 帮 owner 把 keychain 和主要工具链访问管起来 · 不回避密钥这件事 · 反过来正面把它做好。

平台原生 keychain 是真实开发的事实地基 — OS 已经帮人类把"哪个 token 属于哪个 app / 怎么解锁 / 怎么轮换"这些事走通了。 alt 不另起炉灶,直接把OS-native keychain 当成 secret atom 的权威后端:

  • macOS — Keychain Services(security API) · biometric unlock · per-item ACL
  • Linux — Secret Service / libsecret(gnome-keyring / kwallet) · D-Bus 集成
  • Windows — Credential Manager(wincred API) · DPAPI 加密 · per-user vault

具体怎么"接管":

  1. alt creds add <tool> — 一次性引导:从 OS keychain 读已有 token / 或交互式登录 / 或粘 token。所有 tool 走同一个 alt 命令面,owner 不用记每个工具自己的 login 命令(npm login / aws configure / gh auth login 各家语法散乱)。
  2. alt creds list — 列出当前 workspace 装了哪些工具凭据 · 过期时间 · 上次使用 · 来源(keychain / 仓内加密 / 环境变量)。
  3. agent 自动注入 — agent 跑 npm publish / docker push / aws s3 cp / gh pr create 等命令时 · alt 拦截 · 从 keychain 取 token · 临时注入到子进程环境 · 进程结束自动清理。agent 不需要自己处理 token,也看不到 token 实体(除非 explicit unlock)。
  4. alt creds rotate <tool> — 一键轮换:调对应服务的 API 旋转 token / 更新 keychain 条目 / 撤销旧 token / 进 op log。轮换是仓的一等 op · 可 audit · 可 undo(在 grace window 内)。
  5. alt creds revoke <tool> — 紧急撤销:任何 token 怀疑泄露 · 调对应服务 API · 撤销 + 删 keychain · 通知所有 active workspace。是 invariant 1 signed op 一等公民。

跟 secret atom 的关系:keychain item 就是alt://kind/secret 的权威后端实例 · reference 在 alt 仓里 · 真实材料留在 OS keychain。仓搬到新机器时 · alt 提示哪些 secret 需要在新 keychain 上重新提供 · 不会出现"clone 完没法跑"的卡点(只是提示哪些要补,不会傻傻全部要求重输)。 git 出口永远 0 secret: 即使 alt 仓里 secret 是权威 keychain reference + 仓内加密缓存,push --to git 永远只看 path filter + hard gate · 双重保险。

secret op log schema · 永远不记 token 内容

每次跟 secret 相关的动作进 op log,但永远不记 token 实体。op log 自己就是 invariant 2 · signed · append-only · alt-only。

  type:        SECRET_INJECT        # ADD / ROTATE / REVOKE / INJECT / SCAN_FAIL
  ts:          2026-06-21T03:14:17Z
  signed_by:   work@company.com     # 人类 identity (invariant 1) · 不可省
  triggered_by: claude-a@local      # 触发的 agent / human / bot
  controlling: work@company.com     # invariant 7 强制 (agent 必有 controlling)

  secret:
    semantic_id:  github-publish-token       # alt://kind/secret/github-publish-token
    uuid:         01931a8f-7c9f-7000-…       # stable atom id · 跟 atom 一等公民身份一体(§ 12 view A)
    backend:      macos-keychain             # OS keychain ref
    scope_hint:   "service=github.com"       # 哪个服务 · 不含 token

  context:
    cmd:        "npm publish"               # 哪条命令触发注入
    pid:        48211                        # 子进程
    env_vars_injected: ["NPM_TOKEN"]         # 注入了哪些 env (字段名 · 非值)
    duration_ms: 2841                        # 注入持续多久 (子进程生命期)

  # 显式声明 · 永远不会出现的字段:
  # token_value       — 永远不进 op log
  # token_hash        — 不存储 (避免 offline brute)
  # plaintext         — 任何形式都不允许
}

invariant 合约 (secret 操作如何兑现)
1 · signed op secret 操作的 op log 行 必须由 controlling human 签名 · agent identity 不能独立签 secret op(invariant 7 要求)。 agent 触发的 inject 由 alt daemon 用 controlling human 的 key 自动签 · daemon 启动时一次性 unlock(biometric / passphrase)。
2 · op log 5 类 secret op 都入 log:ADD / ROTATE / REVOKE / INJECT / SCAN_FAIL。 schema 见上 · 永远不记 token value / hash / plaintext。 op log 自己 不出 git mirror(默认 alt-only kind)· 即使 attacker 拿到 git 仓也看不到 secret 操作历史。
6 · immutable history secret atom 的 ROTATE 走 alias chain(§ 12 atom mutate 同机制)· 不删旧 entry · 加新 alias · 标 deprecated。 "secret 历史"永远查得到("github-publish-token v3 → v4 at T, rotated by …, reason: …")。 真正泄露时走的不是 immutable 破坏 · 是REVOKE(service API 撤销 + alt 仓 tombstone) — 仓 history 仍完整。
7 · LLM 隔离 agent 永远看不到 secret 实体 · 三道闸: (a) alt 通过子进程 env 注入 token · agent 在 alt 进程内拿不到; (b) 子进程结束后 env 清零; (c) agent 试图直接读 $ALT_KEYCHAIN_* 等 → alt daemon 拦截 · 进 SCAN_FAIL op log · 通知 controlling human。 例外:human 显式 alt creds reveal <id> 可以看 · 但这命令本身必须人工 unlock keychain · agent 跑不通(daemon 拒)。

跟 alt ⊇ git 三轴的关系

本节不是第 4 个 axis · 是把 3 个 axes 统一在一个动机下:

  • alt://axis/format-native(axis 1) — alt 看懂 PDF/PSD/safetensors 的语义 diff · git 出口还是 binary blob · 是脏(binary)/净(text) 的"读"维度
  • alt://axis/visibility(axis 2) — alt 装下 .claude/ 和内部 dev 文档 · git 出口看不见 · 是脏(全收)/净(过滤) 的"路径"维度
  • alt://axis/commit-msg-schema(axis 3) — alt 装下结构化 AI 元数据 · git 出口纯文本 · 是脏(结构化)/净(降级) 的"信息"维度
  • 本节 · delivery polish — 三轴合起来的编辑学总职责,不是新轴,是动机说明

反 framing · 避免误读

alt 不是git 的 lint 工具 · 不是commit msg formatter · 不是squash 脚本。 这些工具假设 agent 写完之后人类手动跑一遍清理 — alt 反过来: agent 自由产出,alt 在 push 边界替它出口干净,人类不需要手动跑任何清理。

也不是git 的简化包装。git 本身没改 · alt 是另一个 VCS,只是 git 在 alt 的出口形式之一(可能还有 hg/jj/sapling 出口,或者 alt-native server-only 不出口)。

为什么 AI 时代这一点是决定性的:

pre-AI 时代,人类自然就写得"干净"(commit 颗粒合适 · 不留 wip 分支 · 不写 AI 元数据),git 不需要 alt 兜底。 AI 时代,agent 的自然产物是大量微 commit + 反复 undo + AI 元数据丰富的 message + 失败 task 分支。 如果 git 直接吃这些 · git 仓很快变成不可读。 git 历史的可读性本质上跟 AI 产出力是冲突的 · 必须有一层编辑学缓冲。 alt 就是这层缓冲 · 这是它跟 git 共存而不是替代的根本理由。
